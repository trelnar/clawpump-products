## 1. [CRITICAL] coinbase.order_status() cannot identify the order it is asked about — list_orders has no client_order_id filter, so _await_coinbase reads an arbitrary account order

**Where** `bot/tradebot/exchanges/coinbase.py:77`

**Trigger** Verified against coinbase-advanced-py 1.8.4: `list_orders(order_ids, product_ids, order_status, limit, start_date, end_date, order_types, order_side, cursor, product_type, order_placement_source, contract_expiry_type, asset_filters, retail_portfolio_id, time_in_forces, sort_by, **kwargs)` (rest/orders.py:1446-1503) has NO client_order_id parameter — `client_order_id` appears only in the order-CREATION helpers. It falls into `**kwargs`, and `RESTBase.get` does `params.update(kwargs)` (rest_base.py:96-99), so it goes on the wire as an extra query param to GET /orders/historical/batch, which filters on order_ids, not client_order_id. `oid` therefore has no effect on which order comes back; `orders[0]` is the first row of an unfiltered, account-wide historical list. Sequence: (1) First $5 Coinbase buy of AAA-USD fills; it is now history. (2) Second buy is placed for BBB-USD. `_await_coinbase` calls `order_status(oid)`; the API returns the account's orders and `orders[0]` is the prior AAA-USD order with status FILLED — terminal on the very first poll (execution.py:120). (3) execute_buy books BBB-USD with AAA-USD's `filled_size` and `average_filled_price`, subtracts AAA-USD's `spent` from the cash table, and because `st == "FILLED"` skips `_cancel_quietly` entirely (execution.py:181-182) — the real BBB-USD GTC limit order is left resting on the book and fills seconds later, untracked. Alternate branch, same root cause: if Coinbase 400s on the unknown query param, the `except` at coinbase.py:80-82 swallows it and returns None on every poll for the full 60s FILL_TIMEOUT_CEX_SEC; `_await_coinbase` then returns `(0, 0, 0, "UNKNOWN", None)`, `_cancel_quietly(None)` returns immediately at execution.py:134-135, and the marketable-limit GTC order — priced at ask*1.0025 — is never cancelled and fills anyway while the bot logs `buy_failed`. There is no fallback identifier: `limit_buy` throws away the placement response `r` (coinbase.py:47-49), which is the only place the real exchange `order_id` is returned.

**Consequence** Every Coinbase order after the first is booked against another order's fill data — wrong qty, wrong price, wrong cash debit — while the actual order stays live and fills untracked. The `_cancel_quietly` unfilled-remainder guard is inoperative in exactly the case it exists for (no status → order_id is None → no cancel). The same call path is used by `execute_sell` (execution.py:263), where a stale FILLED *buy* returned as `orders[0]` makes `proceeds = gross` a buy cost, credits it to cash, closes the position at a fabricated P&L, and leaves the real market sell outstanding. The entire $275 Coinbase leg trades on order state that is not its own.

**Survived refutation because** CONFIRMED against real code and the real SDK; I could not refute it.

The decisive point does not even depend on server behavior: bot/tradebot/exchanges/coinbase.py:74-82 returns `orders[0] if orders else None` and NEVER compares the returned row's client_order_id back against `oid`. _await_coinbase (execution.py:114-130) likewise checks only `o.get("status")`, never identity. The function has no mechanism to establish that the order it read is the order it placed. I searched for a guard elsewhere: order_status has exactly two call sites (execution.py:117, plus two tests), and both tests (test_fills.py:128,139) monkeypatch order_status wholesale, so the 33-test suite never exercises this line.

Reachability holds. config.py:88 VENUES includes coinbase; risk.check_buy imposes no venue restriction and compute_size returns PHASE1_ORDER_USD=$5 for phase 1 — the Coinbase leg is live with $275 behind it.

# Ranked by what fires soonest with real money

## 1. Solana buy books qty=0 and throws the position away — `execution.py:195`

**Fires on the first Solana buy, and every one after. Not probabilistic.**

`_await_solana` (execution.py:145-151) returns "ok" the moment `confirm()` reports `confirmationStatus == "confirmed"` — typically the poll at t≈3s. Line 195 then calls `solana_dex.token_balance(mint)`, whose `_rpc` (solana_dex.py:25-32) sends `getTokenAccountsByOwner` **with no commitment field**, so the node answers at the JSON-RPC default, `finalized`. Finalized trails confirmed by ~32 slots (~13s), permanently. The read is *structurally* behind the confirmation that just released it — there is no timing window where it wins. `after == before`, `qty = 0`, line 211 raises, and the `except` at 213-217 books it as a failure.

The authors knew about this exact class of problem and applied the fix one function away: `token_decimals`' docstring (solana_dex.py:59-62) says "token_balance() reports 0 when no associated account exists yet, so raw→whole conversion cannot rely on it for a first buy." They fixed the decimals read and left the balance read.

**Cost to the owner:** $5 of USDC gone from the Solana wallet, real tokens sitting in it, no positions row. Telegram says `NOT BOUGHT` — the exact opposite of what happened. The tokens get no invalidation stop, no profit plan, no liquidity-drain exit, and `flatten_all` iterates `state.positions()` (execution.py:323) so the FLATTEN kill switch cannot reach them either. Nothing recovers this: `reconcile_cash` (monitor.py:72-82) pulls USDC balances only; `upsert_position` has exactly two callers, both in `execute_buy`/`execute_sell`. And because approval whitelists the asset *before* the buy runs (approval.py:101), the next agent ticket for the same token auto-buys with no approval and strands another $5 the same way. This repeats silently until the owner reads a block explorer.

**Verdict: BLOCKING.** This is the single most likely thing to happen the first time the owner types YES. $390 of the $880 is on this leg. Fix: pass `{"commitment": "confirmed"}` in the `_rpc` config object, and fall back to the Jupiter quote's `outAmount` (currently discarded into `_q` at execution.py:190) when the delta is zero.

## 2. Coinbase order status is not the order you asked about — `coinbase.py:76`

**Fires on the first Coinbase order, in one of two ways.**

`list_orders(client_order_id=oid)` — verified against the installed 1.8.4: the parameter does not exist, it lands in `**kwargs`, `RESTBase.get` does `params.update(kwargs)`, and it goes on the wire as an unrecognized query param to `GET /orders/historical/batch`, which filters on `order_ids`. `order_status` then returns `orders[0]` and **never compares the returned row's identity back to `oid`** — that is the part that doesn't depend on guessing server behavior.

- **API accepts and ignores the param:** `orders[0]` is an arbitrary row from the account's order history. And because `st == "FILLED"` skips the cancel at execution.py:181-182, the real order is left resting as a GTC limit at ask×1.0025 and fills untracked. A non-FILLED foreign row is worse: `_cancel_quietly(o.get("order_id"))` cancels somebody else's order.
- **API 400s on the unknown param:** `except` at coinbase.py:80-82 swallows it, returns None on every poll for the full 60s, `_await_coinbase` returns `(0,0,0,"UNKNOWN",None)`, `_cancel_quietly(None)` returns immediately (execution.py:134-135), the marketable limit is never cancelled and fills anyway, and the bot logs `buy_failed`. Same outcome as #1: untracked position, false NOT BOUGHT alert.

`execute_sell` shares the path (execution.py:263) and does `proceeds = gross` — a stale FILLED *buy* row credits a buy cost to cash, closes the position at a fabricated P&L, and leaves the real market sell outstanding.

**Cost to the owner:** the entire $275 Coinbase leg trades on order state that isn't its own, and the unfilled-remainder guard is dead in exactly the case it exists for.

**Verdict: BLOCKING.** Fix is small and there are two of them: `limit_buy` already returns the placement response `r` (coinbase.py:49) carrying the real exchange `order_id` — the caller discards it at execution.py:179. Keep it, poll with `get_order(order_id)`, and assert the returned `client_order_id` matches.

## 3. Any RPC error after broadcast strands the position — `execution.py:195, 206, 142-152`

Same window as #1 but triggered by an exception rather than staleness, and it covers Base too. Once `solana_dex.swap` (190) or `evm_dex.swap` (202) returns, the money is spent. Every call after that point — `confirm()` inside `_await_solana`, `token_balance` at 195/206 — is unguarded, and `_rpc` raises on both `raise_for_status()` and any `"error"` in the body, with no retry. The default endpoint is public `api.mainnet-beta.solana.com` (config.py:33), which 429s routinely. Anything raised lands in the blanket `except` at 213 and the position is never booked. The 90s `FILL_TIMEOUT_SOL_SEC` expiring is a third route to the same place — `confirm`'s own docstring (solana_dex.py:118) concedes "a dropped tx can still land later."

**Cost to the owner:** identical to #1 — $5 and a permanently invisible position, unreachable by FLATTEN.

**Verdict: BLOCKING, and it's the same fix.** Everything after broadcast belongs in its own try/except that books the position on best-effort quantity rather than discarding it. `execute_buy`'s docstring says "Nothing is booked before confirmation" — the code guards the phantom-position direction and leaves the unbooked-real-position direction wide open. The `RECON_FREEZE` machinery at execution.py:234-241 is already the right landing pad for an uncertain fill; this path just doesn't use it.

## 4. REVOKE never revokes anything — `approval.py:48, 71`

`handle()` uppercases the whole command line before parsing, so `REVOKE solana:DezXAZ8z…` reaches `whitelist_revoke("SOLANA:DEZXAZ8Z…")`. `asset_id` is `TEXT PRIMARY KEY` with no `COLLATE NOCASE` (state.py:19), so the UPDATE matches zero rows. `rowcount` is never checked; the owner is told "Revoked … It will require approval again," and `journal.log_event("whitelist_revoke", …)` writes a revocation into the append-only audit log that did not occur. Asset ids carry a lowercase scheme prefix on every venue (`solana:`, `base:`, `cex:`), so this misses for all three — `cex:` is not a survivor.

**Cost to the owner:** the only per-asset way to withdraw standing buy authorization is inert while reporting success. `is_whitelisted` keeps returning True, so every later BUY_NOW/ADD for that token skips Telegram entirely (execution.py:62-63). This matters most on the path core.py already documents — an approved-but-blocked asset "stays whitelisted and will auto-buy if it requalifies." $5 per unattended order at phase 1; ~$44 at phase 4.

**Verdict: BLOCKING, and it is a one-line fix** (take `arg` from the original-case `text.split()`). It costs nothing today only because the owner hasn't tried to use it yet. Ship a bot whose kill-authority commands lie to you and you will not find out until you need them.

## 5. An ADD keeps the old stop — `state.py:111-113`

`upsert_position`'s UPDATE branch sets only `qty` and `cost_basis_usd`. `invalidation`, `entry_liq` and `group` are accepted in the signature and used **only in the INSERT branch**. `execute_buy` passes a fresh `invalidation=ticket.get("invalidation_price")` on every ADD (execution.py:227-228), and `runner.py:189-191` always populates it (`wave_invalidation or invalidation_price`; `invalidation_price` is required by the forecast schema). It is silently dropped. `monitor.py:48-51` is the only reader and gates the stop on the stale column. The author special-cased the *other* revised exit parameter for this exact case one line later — `set_position_plan(asset, plan)  # an ADD carries a revised plan` — with no equivalent for the stop.

**Cost to the owner:** the doubled position is protected at whatever level the agent set before the run-up. On a $10 combined phase-1 basis with entry $1.00, a raised stop at $1.70 discarded, price retraces from $2.00 → $0.86 and nothing fires; ~$8.60 given back where the agent's stated stop was roughly break-even. Direction also inverts: a *lowered* stop being discarded fires an exit the agent didn't want. Either way the books carry a stop nobody chose, on every ADD, with no alert.

**Verdict: fix before the first ADD — which in practice means before the first trade,** because the agent files ADDs on its own schedule and you can't gate it. Two lines in the UPDATE branch.

## 6. A partially filled Coinbase exit deletes the whole position — `execution.py:264, 309`

`execute_sell` binds `st` from `_await_coinbase` and tests only `if sold <= 0`; `st` is then dead, and unlike the buy path five lines above there is no `_cancel_quietly` for the sell remainder. Line 309 keys the close on the **requested** `fraction`, never on `sold`, so a 40% fill on a `fraction=1.0` exit runs `close_position` and DELETEs the row while 60% of the tokens sit at the venue. Reachable via Coinbase Advanced Trade price-protection on a thin book (partial fill, remainder cancelled) and via the 60s timeout break at execution.py:120-121 returning a partial snapshot on a still-OPEN order — in that case no cancel is issued at all.

**Cost to the owner:** the remainder is orphaned permanently — invisible to `total_value`, to the 20% drawdown series, to the 5%-per-position cap and to FLATTEN. The alert reports P&L using `cost_part = cost_basis_usd * fraction`, i.e. 100% of basis against a 40% fill, so the number is wrong (over-reporting the loss) and the orphan is never noticed. The `fraction < 1` variant is worse in a quieter way: line 312 subtracts actual `sold` qty against fraction-scaled cost, which drops the recorded entry price and arms every later profit-plan multiple early.

**Verdict: can wait past the first trade, but not past the first Coinbase position.** It needs an actual partial fill, and $5 orders on liquid CEX books usually fill whole.

## 7. A model plan revision re-arms already-fired legs — `state.py:156`

`set_position_plan` returns early only on exact dict equality; any difference anywhere deletes `plan_done` wholesale, including for legs whose `(multiple, sell_fraction)` are unchanged and whose level is already crossed. The model is told every held position needs a HOLD/ADD/SELL_NOW decision each cycle (runner.py:100-105), `held_context` sends the full standing plan but **no completion state** (runner.py:68-80), so a model that raises only the final target and re-sends leg 0 verbatim is behaving correctly and still causes an unintended sale. `MONITOR_INTERVAL_TOKEN_SEC = 5` vs `DISCOVERY_INTERVAL_SEC = 900`, so the re-fire lands within 5 seconds of the revision, long before price can leave the level. Entry price genuinely survives the first partial exit (execution.py:307-312 scales qty and cost together), so the level is still crossed.

**Cost to the owner:** 50% of the remainder sold per differing revision, geometrically stripping the runner the whole 2x-10x thesis depends on, each one paying a full DEX round trip that gate 4 tolerates up to ~9%. Logged as an ordinary `profit_plan_leg` — completely silent.

The docstring at state.py:145-148 argues "a genuinely new plan does clear them: its legs are different legs." That is false for a partial revision. The pinning test (test_fills.py:253-260) only covers the case where the fired leg's own fraction changed.

**Verdict: can wait — but only until the first position reaches its first profit-plan leg,** which could be day one if a token runs. Fix is to key completion on `(multiple, sell_fraction)` rather than index, and to send fired-leg state in `held_context`.

## 8. `plan_done` is resurrected after `close_position`, disarming that leg on re-entry — `monitor.py:35` (your #3 and #6, same defect)

`close_position` deletes the `plan_done` kv row (state.py:125); `execute_sell` then returns "filled"; `monitor.py:34-35` runs `mark_plan_leg_done` *afterwards*, re-creating the row for an asset with no position. The `dust` returns at execution.py:274/288 reach it too. On re-entry, `upsert_position` takes the INSERT branch which already stores the plan, so `execution.py:229`'s `state.position_plan(asset) != plan` is False and the only other clearer never runs. The asset is still whitelisted, so the re-entry needs no approval.

**Cost to the owner:** the final full-exit leg is skipped for the life of the new position. Durable in SQLite across restarts.

**Verdict: can wait.** It needs an exit through a plan leg *and* a re-entry into the same asset — both downstream of trades that currently cannot complete. Fix is one line: mark the leg before calling `execute_sell`, or have `close_position` run last.

## 9. Negative `sell_fraction` deletes a live position without selling — `core.py:124`

`sell_fraction` is a bare `{"type": "number"}` in the schema (prompts.py:92) — contrast profit-plan legs, which `runner._plan_of` bounds at `0 < frac <= 1` (runner.py:136), proving the authors knew fractions need a mechanical bound. `runner.py:166`'s `or 1.0` only rewrites falsy values; `core.py:124`'s `min(float(frac), 1.0)` clamps the high side only. `-0.5` reaches `execute_sell`, `amt = int(raw * fraction)` is negative, the `amt <= 0` dust branch fires, `close_position` runs, no swap is submitted, the ticket is marked done, no alert. Coinbase is not affected (negative qty errors into `failed` with the position intact).

**Cost to the owner:** tokens held, position row gone, all four safety mechanisms including FLATTEN dead for them.

**Verdict: can wait, but fix it in the same pass as anything else** — it is a one-character clamp (`max(0.0, min(...))`) guarding a permanently stranded position. Reachability requires an out-of-contract model output, which is unlikely but is not a code hypothetical: this is an unvalidated untrusted input in a pipeline whose payload explicitly carries attacker-influenceable scraped content (`runner.py:90`, `untrusted_market_data`).

# The must-fix set

Nothing in this list is a rewrite. Before the first YES: **#1, #2, #3, #4, #5.** That is a commitment parameter, an order-id round-trip, one try/except around the post-broadcast block, one `.upper()` moved off the argument, and two columns added to an UPDATE. #6-#9 are real and should be fixed in the same sitting, but none of them can fire until a trade has actually completed, and right now none can.

The pattern worth stating to the owner plainly: **seven of the eight defects are in the code between "the money left" and "the books were written," and all of them fail in the same direction** — real assets exist that the database does not know about. The gates are well-built and defend the entry. The system has no defense at all on the other side, because `reconcile_cash` only reconciles cash. There is no code anywhere in the package that reads a token balance and asks "should this be a position?" That absence is what turns each of these bugs from an accounting error into a permanent loss, and it is why they cluster: the fix that would have caught all of #1, #2, #3, #6 and #9 as a $5 anomaly instead of a stranded position is a startup-and-periodic position reconciliation against venue holdings. That is a bigger change than the five one-liners, but it is the actual structural gap.

# The unknown that code review cannot resolve

**Whether this bot can get out of a position at a real venue at all.**

Every safety mechanism in the system — the invalidation stop, the standing profit plan, the liquidity-drain exit, agent SELL_NOW, and the owner's FLATTEN kill switch — terminates in the same `execute_sell`, and `execute_sell` has never sold anything anywhere. Code review can confirm its logic is internally coherent. It cannot answer any of the questions that decide whether a sell actually clears:

- **Will Jupiter route a sell of a thin memecoin at 600 bps?** Gate 4's `exit_safety` is a *quote*, not an execution. Quotes are systematically optimistic for exactly the tokens this bot hunts — transfer hooks, freeze authority, blacklists, a fee-on-transfer that a quote simulates cleanly and a signed transaction reverts on. A token that quotes sellable and is not sellable passes every gate in this codebase.
- **Is there gas?** `sol_balance()` is defined at solana_dex.py:35 and, by grep, called from nowhere. There is no native-balance preflight on either chain. If the $390 Solana wallet holds no SOL or the $215 Base wallet holds no ETH, the exit is the thing that discovers it — and unlike a failed buy, a failed exit happens while you are already holding.
- **Does a $5 Coinbase order clear the product's minimum base size?** And does the *remainder* of a partial exit clear it? A residual below `base_min_size` is unsellable by any automated path.
- **Does the Coinbase key actually have trade scope on the portfolio holding the $275, and is the Solana keypair the funded wallet?** Never demonstrated against a venue.

The right way to resolve it is not more reading. It is one manual round trip, by hand, on the smallest possible size, on each of the three venues — buy, confirm the books match the venue, sell, confirm the cash comes back — before the agent is allowed to file a ticket that reaches `execute_buy`. Every finding above is something I can prove from the source; this is the one thing that only contact with a real venue can tell you, and it is the one that determines whether "$5 at risk" means $5 at risk or $5 permanently stuck in a token the bot cannot leave.
